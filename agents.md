## Mission and product boundaries
Uber Welcome is the **existing GitHub Pages web app** used in a 2023 Chevrolet Tahoe for an Uber Black/VIP passenger experience. The passenger display runs on an iPad; the driver controls it from an iPhone via `admin.html`. **Do not confuse this project with ABOARD**, a separate, newer app. Preserve the currently working passenger welcome, Explore Miami, advertising, languages, Halloween, music shortcuts and ETA.

Production URLs:
- Passenger: https://rabermudezg13.github.io/uber-welcome/
- Driver admin: https://rabermudezg13.github.io/uber-welcome/admin.html

## Architecture
- Static vanilla HTML/CSS/JS served by GitHub Pages: `index.html` (passenger) and `admin.html` (driver).
- `firebase-config.js` exports Firebase client configuration. Firebase Realtime Database syncs driver actions to passenger display.
- Firebase JS SDK 10.12.2 imported from Google CDN. No local build system or native Xcode project is established by this repository.
- Third-party QR images are generated by `https://api.qrserver.com/v1/create-qr-code/`; this sends the encoded invitation URL to that external service. Consider a local QR generator in future for privacy/reliability.
- Spotify track buttons in admin open Spotify links. They are not authenticated Spotify playback API controls.
- The repository README contains old Firebase test rules and mentions a static Spotify QR asset; prefer the actual live code for behavior.

## Shipped features, confirmed merged to main
### 1. Live ride ETA (PR #9, merged; refined in PR #12, merged)
- Driver sets an initial ETA (minutes) and sends ride details to the iPad.
- Passenger countdown ticks automatically each second, derived from synchronized ride fields.
- Driver controls: **Pause ETA**, **Resume ETA**, **− 1 min**, **+ 1 min**. Each tap adjusts **60 seconds** (previously 300 seconds/5 minutes). Do not regress to 5-minute steps.
- Firebase `ride` fields: `estimatedMinutes`, `etaRemainingSeconds`, `etaPaused`, `etaUpdatedAt` (client timestamp in milliseconds), plus `passengerName`, `language`, `honorific`, `updatedAt`.
- Driver ETA calculation: remaining seconds are the stored `etaRemainingSeconds` minus elapsed time since `etaUpdatedAt`, except when `etaPaused` is true. Clamp to zero. The passenger computes/display updates on its own timer.
- The countdown is **manual, not GPS or traffic-aware**. Driver adjusts it for delays, detours, traffic or a bridge. Keep pause/resume and both views in sync.
- Reset clears ride ETA and returns screen to Welcome.

### 2. Dynamic Spotify Jam invitation QR (PR #10, merged)
- Driver starts a Spotify Jam **in Spotify**, copies the current session invitation URL and pastes it into the admin's Spotify Jam QR field.
- `Share Jam QR to iPad` writes `spotifyJam: {url, updatedAt}` to Firebase RTDB.
- Passenger app subscribes to `spotifyJam`, generates a QR for the current link and displays **Join Our Spotify Jam** on both the Welcome and Explore Miami views.
- `Hide Jam QR` deletes `spotifyJam` from Firebase. `Reset for Next Passenger` also clears `spotifyJam` so a stale session link is not shown to the next passenger.
- Current client validation requires HTTPS and host `open.spotify.com` or `spotify.link`. It does not prove that a link is a valid/active Jam.
- The app **cannot create Spotify Jam sessions via a public Spotify API**, automate Spotify's internal Create/+ UI, or guarantee that an old QR will remain valid. New Jam = paste the new link.
- Spotify Jam session creation and participation depend on Spotify's current eligibility/account rules. Do not claim this feature starts a Jam or streams audio itself.
- Spotify QR is rendered via third-party QR endpoint; never display a QR unless there is a valid current URL.

## Firebase state contract
- `ride`: passenger data and ETA state. Writing the full `ride` object can overwrite other ride fields; preserve fields as needed for future features.
- `screen`: `welcome` or `explore`.
- `theme/halloween`: boolean.
- `spotifyJam`: `{ url: string, updatedAt: number }` or `null`.
- Admin and passenger listen using `onValue` and write using `set` or `update`.
- Test changes across two devices/tabs to verify real-time sync and reset behavior.

## Security and reliability issues to address before scaling
- Current README suggests permissive RTDB test rules (`.read: true`, `.write: true` for ride). These are NOT production-safe. Inspect deployed Firebase rules and introduce authenticated admin writes, least-privilege reads, and input validation; do not assume the rules are already secure.
- Avoid exposing Spotify access tokens, refresh tokens or client secrets in public GitHub Pages JavaScript, QR URLs, Firebase public data or passenger iPad.
- The current `spotifyJam` link is stored in Firebase and passed to the external QR provider. Evaluate privacy, access control, expiry and third-party reliability.
- Protect against malformed URLs, stale sessions, missing network, cross-device clock skew, Firebase disconnects, and repeated taps.
- No evidence of an automated test suite or native Xcode project in this repo; add tests without breaking the static site.

## Suggested Xcode continuation
1. First decide whether the goal is a **native iOS/iPadOS app** or a SwiftUI `WKWebView` shell around the existing GitHub Pages app. Do not replace the functioning web app without approval.
2. For a native shell, preserve Firebase paths and UI semantics, including Welcome/Explore, ETA ±1 minute, pause/resume, Jam URL entry/clear and QR display. Keep the existing web deployment available as fallback.
3. If building native UI, use SwiftUI, Firebase RTDB observers, async-safe state updates and a native Core Image QR generator to avoid third-party QR services.
4. Add a driver-only settings/control interface and a passenger-safe, read-only presentation surface. Prevent passengers from changing ETA or driver settings.
5. Add validation/tests: Jam link replaced updates QR immediately; Hide/Reset hides it; ETA ticks, pauses, resumes, ±60 seconds, clamps at zero; offline and background/resume behavior; multilingual/Halloween regressions.
6. Build Spotify search/playback only after confirming API access, account prerequisites and a secure server-side OAuth/token architecture.
7. Coordinate changes through GitHub feature branches and PRs; verify mergeability and avoid parallel stale branches.
